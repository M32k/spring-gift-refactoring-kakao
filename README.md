### 2. 사용한 프롬프트와 접근 방법

- **목록부터 받고, 확인한 뒤 파일로 쓰기**: AI에게 먼저 들어갈 내용이나 초안을 보여 달라고 했다. 내용을 확인한 뒤에 파일을 만들거나 고치게 했다.
  > 방금 만든 CLAUDE.md를 기준으로 AGENTS.md를 만들 거야. 아직 파일은 만들지 말고, 들어갈 내용부터 보여 줘.

  > README.md에 1단계 AI 활용 기록을 쓸 거야. 아직 파일은 고치지 말고 초안만 보여 줘.
- **manual mode**: 문서 작성을 시작할 때부터 썼다. 1단계는 `src/` 수정 금지라서, 파일이 바뀔 때마다 직접 보고 승인하려고 썼다.
- **범위를 정한 분석 요청**: 주문 흐름 분석을 요청할 때 세 가지를 정했다.
  - 주문 관련 코드만 읽는다.
  - 읽을 것이 15개를 넘으면 먼저 묻는다.
  - 결과를 (확인함)과 (코드로만 판단)으로 나눈다.
- **확인함 / 코드로만 판단 구분**: 결과마다 근거를 표시했다. 직접 요청을 보내 본 결과에는 **(확인함)**, 코드만 읽고 내린 판단에는 **(코드로만 판단)**을 붙였다.
- **확인 방법으로 섹션 나누기**: 확인 필요 목록을 세 섹션으로 나눴다.
  - A: 요청으로 확인함
  - B: 코드로만 확인함
  - C: AI 추정
  - 요청으로 확인한 항목은 A로 옮겼다. 다른 문서가 번호로 가리키기 때문에 번호는 다시 매기지 않았다.
- **작동과 이유 나누기**: 작동을 만드는 코드 위치와, 작동의 의도를 설명하는 근거(주석, 메시지, 이름)를 따로 적게 했다.
- **고치지 않고 기록만**: 버그처럼 보이는 작동도 고칠 방법을 정하지 않고 기록만 하게 했다.
- **용어 사전으로 표현 맞추기**: 용어 사전을 만든 뒤 모든 문서의 표현을 용어 사전에 맞췄다.
- **역할 나누기**: 요청 확인(curl)과 git 명령은 내가 직접 했다. AI는 보낼 요청을 적어 주기만 했다.
- **범위 제한**: 프롬프트마다 "`src/`는 건드리지 마", "다른 부분은 건드리지 마"처럼 고쳐도 되는 범위를 적었다.

#### `/init`이 만든 CLAUDE.md에서 AGENTS.md로 옮기지 않은 내용

AGENTS.md에는 저장소를 읽어서 알 수 없는 것과 다시 찾는 데 오래 걸리는 것만 남겼다. 지금 CLAUDE.md는 `@AGENTS.md` 한 줄이다.

| CLAUDE.md 내용 | 뺀 이유 |
|---|---|
| 빌드는 Kotlin 설정이지만 코드는 전부 Java이고, `src/main/kotlin`은 비어 있다 | `build.gradle.kts`와 `src/` 폴더 구조를 보면 바로 알 수 있다 |
| ktlint는 Kotlin만 검사해서 지금은 아무것도 검사하지 않는다 | `build.gradle.kts`의 플러그인 설정에서 알 수 있다 |
| H2 인메모리 DB와 Flyway로 뜨고, 재시작하면 데이터가 초기화된다 | `application.properties`에 datasource 설정이 없다는 점과 `db/migration`에서 알 수 있다 |
| 테스트는 아직 없다 | `src/test`를 보면 바로 알 수 있다. 2단계에서 바뀔 내용이기도 하다 |
| 문서는 한국어 평서문(~다)으로 짧게 쓴다 | 기존 문서를 보면 알 수 있다 |

| **(확인함)** / **(코드로만 판단)** 표시 | 정의가 주문 흐름 문서 머리말에만 있고, 주문 흐름 문서는 넣지 않기로 했다. 대신 "요청 확인은 사용자가 한다"는 결정을 남겼다 |
| 작업 문서는 `docs/work/NN-주제/`에 두고 머리말을 붙인다 | 주문 흐름 문서에만 해당하는 규칙이라 뺐다 |

| user-stories의 "왜: 확인 필요"와 "확인한 응답"은 실제로 본 것만 쓴다 | `docs/user-stories.md` 머리말에 적혀 있다 |
| 커밋 메시지는 `접두사: 한국어 요약` 형식으로 쓴다 | `git log`로 알 수 있다 |

### 2. 사용한 프롬프트와 접근 방법

- **인수 조건부터, 파일보다 먼저 전체를 보기**: 테스트 코드 전에 인수 조건만 쓰게 했다. 파일에 쓰기 전에 시나리오 전체를 먼저 받아 확인했다.
  > 2단계 인수 테스트를 시작할 거야. 먼저 인수 조건만 써 줘.

  > 파일에 쓰기 전에 시나리오 전체를 먼저 보여 줘.
- **인수 조건 형식을 정하기**
  - 상황과 결과에 구체적인 수를 넣는다.
  - 한 시나리오에는 행동을 하나만 담는다.
  - 구현 용어 대신 용어 사전의 말을 쓴다.
  - 빠진 시나리오는 정상 흐름, 입력 검증, 오류 상황으로 나눠 목록으로만 받는다. 파일에는 넣지 않는다.
- **결과와 확인 방법 나누기**: 인수 조건에는 결과만 적었다. 포인트를 어디서 확인할지는 테스트 환경을 정할 때 따로 정했다.
- **계획부터 받기 (plan mode)**: "정해진 것"과 "계획에 넣어 줄 것"을 나눠 주고 계획만 받았다. 선택지가 여러 개인 곳은 장단점을 함께 받아 내가 골랐다.
  > 테스트 데이터 전략: 모든 시나리오가 초기 데이터에서 시작하고, 어떤 순서로 실행해도 같은 결과가 나오게 하는 방법. 선택지가 여러 개면 장단점과 함께 보여 줘.
- **바꿀 수 있는 범위 정하기**: `src/main`은 고치지 않는다. 바꿀 수 있는 것은 `build.gradle.kts`의 테스트 의존성, `src/test`, 테스트용 설정 파일뿐이다.
- **실행은 내가**: 테스트 실행, curl, git 명령은 내가 터미널에서 했다.
- **일부러 실패시켜 확인하기**: 통과만 보지 않고, 기대값을 일부러 틀리게 바꿔 해당 시나리오만 실패하는지 확인했다.
- **정의한 스킬**: `/acceptance-test` (`.claude/skills/acceptance-test/SKILL.md`)
  - 인풋: 스토리 번호 하나. 생략하면 feature 파일 위치가 없는 스토리 중 범위가 작은 2~3개를 추천받고 고른다.
  - 스킬에 모은 "두 번 이상 고친 것":
    - 현재 작동 확인, 테스트 실행, git은 사용자가 한다.
    - 인수 조건의 수는 초기 데이터에서 가져온다. 회원 id와 user 번호가 어긋난다(user1은 회원 2번).
    - 새로 만든 것은 응답에 나온 번호로 다음 요청을 보낸다.
    - 포인트만 DB에서 확인하고, 나머지는 API로 확인한다.
    - 버그처럼 보여도 고치지 않고 테스트로 고정한 뒤 open-questions에 남긴다. 번호는 다시 매기지 않는다.
    - 통과만 믿지 않는다. 기대값 하나를 일부러 틀리게 바꿔 실패를 본다. 너무 빨리 끝나면 `--rerun-tasks`로 다시 실행한다.
    - 시나리오마다 Flyway clean + migrate로 초기 데이터로 되돌린다.

### 2. 사용한 프롬프트와 접근 방법

- **규칙을 먼저 문서로**: AGENTS.md에 "3단계 작업 규칙"을 적고 시작했다. 구조 변경과 작동 변경을 한 커밋에 섞지 않는다. 인수 테스트를 고치지 않는다. `@Valid`, `@Transactional`, `@ExceptionHandler`, `orElse(null)`과 404, 응답 DTO 필드 이름은 건드리지 않는다. 버그처럼 보여도 고치지 않고 "작동 변경 후보"에 적는다.
- **한 번에 한 항목**: 지금 할 일이 tasks.md에 적혀 있어야 코드를 고치게 했다.
  > docs/work/05-service-layer/tasks.md의 Op1을 하자. 먼저 계획만 보여 주고 파일은 아직 고치지 마.
- **옮길 때 지킬 것을 요청에 적기**: 확인 순서, 예외 메시지, 404를 알리는 방법(서비스는 `Optional`이나 결과 enum, 응답은 컨트롤러), 더하면 안 되는 확인을 요청에 적었다.
  > 등록: 확인 없이 save. 같은 이름 확인을 더하지 마(open-questions 26번, 10-7의 500을 그대로 둔다).
- **순서를 지키는 시나리오**: 확인 순서가 바뀌면 응답이 달라지는 경우를 일부러 넣었다. 없는 상품에 틀린 옵션명(11-6, 404가 아니라 400), 옵션이 1개인 상품에서 없는 옵션 삭제(12-6), 없는 카테고리를 빈 이름으로 수정(10-9).
- **curl을 먼저**: 스킬 초안에 "(확인 안 함)"이 붙지 않게, 요청으로 확인한 값을 먼저 넘겼다. 실패해야 하는 요청을 먼저 보내고, 상태를 바꾸는 요청은 나중에 보냈다.
- **문서는 범위를 정해서**: 같은 문장이 여러 스토리에 있어 다른 스토리까지 바뀐 뒤로, "12번 범위 안에서만 고쳐 줘"처럼 고칠 범위를 적었다.
- **포맷 검사를 테스트보다 먼저**: AI가 쓴 줄이 포매터 모양과 다른 일이 잦아서, `./gradlew spotlessCheck`를 먼저 돌렸다.
- **검토는 맥락 없이**: 구현한 세션을 계획 모드로 두고, 작업 기억이 아니라 `190a6b8`과 지금 코드를 나란히 비교하게 했다.
  > 지금까지 이 세션에서 한 작업 기억에 기대지 말고, git과 파일만 근거로 처음 보는 사람처럼 검토해 줘.

### 2. 사용한 프롬프트와 접근 방법

- **규칙을 먼저 문서로**: AGENTS.md에 "4단계 작업 규칙"을 더하고 시작했다. 작업마다 tech-spec을 먼저 쓰고, 바뀌지 않아야 할 작동마다 지키는 테스트를 붙이고, 트레이드오프가 있는 결정은 ADR로 남긴다.
- **테스트를 먼저 고치고 실패를 남기기**: 바꿀 작동의 테스트를 먼저 고치고, 코드를 바꾸기 전에 실패하는 출력을 tasks.md에 붙인 뒤에야 코드를 바꾸게 했다.
  > B1의 "테스트 먼저"만 해 줘. 리스너, ADR, src/main은 아직 만들지 마.
- **비교표를 받고 내가 고르기**: 선택지가 있는 곳은 AI에게 비교만 시키고 결정은 내가 했다.
  > REQUIRES_NEW를 어느 빈의 어느 메서드에 붙일지는 코드에 넣기 전에 이유와 함께 먼저 알려 줘.
- **구조 변경 전에 특성화 테스트**: 테스트가 없는 작동(알림 요청 모양, 금액 넘침, 이름 검증 메시지 전체)은 리팩터링 전에 지금 코드에서 통과하는 테스트로 고정했다.
- **상태를 다시 조회**: 응답 코드만 보지 않고 재고, 포인트(DB), 위시 목록, 알림 상태(DB)를 다시 조회하게 했다.
- **코드에 넣기 전에 묻기**: 트랜잭션 위치처럼 이유가 필요한 결정은 "코드에 넣기 전에 이유와 함께 먼저 알려 줘"라고 적었다.
- **`파일:줄`은 쓴 뒤 대조**: 문서를 고칠 때마다 참조를 지금 코드와 대조한 표를 받았다.

AI가 처음 낸 제안 중 일부는 커밋 전에 고쳐져 저장소에 남지 않았다. 근거 칸은 최종 결정이 남은 곳이다.
